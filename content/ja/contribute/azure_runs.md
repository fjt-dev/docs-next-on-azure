Azure のサブスクリプションにリソースを作る作業のためのルールです。費用と後片付けの思わぬ事態を防ぐためにあります。人にも、コーディングエージェントにも適用します。

## 実行の前に

1. サブスクリプション、リージョン、リソースグループの名前を、メンテナーに確認します。決めつけないでください。
2. 実行ごとに、**新しい専用のリソースグループ**を使います。以前からあるグループを再利用しないでください。
3. 各段階(プロビジョニング、デプロイ、検証、削除)に厳しい期限を持つ**時間枠**と、**費用の上限**を決めます。始める前に、両方を作業ログに書きます。
4. 継続的な料金のあるもの(たとえば Front Door Standard)は、先に、Azure の価格ページで現在の価格を確認します。
5. 先にローカルで確認します(Functions Core Tools + Azurite)。実際の Azure は、ローカルのスタックでは分からないことだけに使います。

## 実行の間

- 長いコマンドには、すべて、明示的な時間制限を付けます。
- 作成したすべてのリソースの名前を、作成しながら記録します。
- Flex Consumption のデプロイ用コンテナーには、書き込まないでください。プラットフォームが埋めます。

## 実行のあとで

1. 作成したリソースを、自分の記録から、**名前で 1 つずつ**削除します。リソースグループ自体は、この実行で作ったときだけ削除します。
2. グループの読み取り専用のインベントリで、削除を確認し、**翌日**にもう一度インベントリを取ります(Front Door のプロファイルやストレージアカウントのように、論理削除されたり、遅れて消えたりするリソースが残ることがあります)。
3. [作業ログ](../plan/worklog.md)に記録します。何を作ったか、何を測定したか、費用はいくらか、何を削除したか。

## 資格情報

- リポジトリにも CI の変数にも、シークレットを入れません。CI は、GitHub の OIDC フェデレーションを使います。
- キーより、マネージド ID とロールの割り当てを優先します。ストレージアカウントでは、共有キーのアクセスを無効にしています。

## 最初の実行(2026-11-06)で学んだこと

- **`az bicep build`、`az deployment group validate`、`what-if` は、デプロイすると失敗するテンプレートを通します。** 間違った組み込みロール定義 ID(`RoleDefinitionDoesNotExist`)は、実際のデプロイでしか見つかりませんでした。そのような ID は、`az role definition list` の出力に対するテストで固定し、最初の実際のデプロイは、1〜2 回失敗すると見込んでください。
- **デプロイするものを、そのまま動かしてください。** ローカルのスタックは、zip の元になったディレクトリを動かしていたので、シンボリックリンクを失ったパッケージ(Azure はリンクを落とします)が、ローカルのテストをすべて通りました。今は、スタックが、展開した zip を動かします。
- **まず、ホスト自身のログを読んでください。** `az monitor app-insights query --app <name> -g <rg> --analytics-query "traces | order by timestamp desc"` は、1 分以内に、見つからないモジュールとともに `Worker was unable to load entry point` を示しました。HTTP のレスポンス(Azure の既定の "up and running" ページ)は、何も語りませんでした。Application Insights の反映は、1〜3 分遅れます。
- **残したい設定を、`az functionapp config appsettings set` で設定しないでください。** 次のテンプレートのデプロイが、すべて置き換えます。Bicep テンプレートに入れてください。
- **アイドルのインスタンスは、数分で消えます。** そのため、新しいインスタンスが必要な測定には、数分間のトラフィックなしが必要で、インスタンスより長く続く遅延処理は、失われます。
- 進めながら、タイムスタンプ付きの記録を残してください(開始時刻、厳しい停止時刻、リソース名)。一覧があれば、後片付けは機械的な作業になります。
- **`validate` と `what-if` が見逃す、もう 1 つの種類のエラー: Azure Monitor と ARM が、デプロイのときにだけ確認する値**(`QueueMessageCount` アラートのウィンドウ、組み込みロールの ID)。そのような制約は、最初に当たったときに、必ずテストで固定してください(`packages/tests-unit/src/unit/bicep.test.ts`)。新しい種類のリソースでは、最初のデプロイの失敗を、見込んでおいてください。
